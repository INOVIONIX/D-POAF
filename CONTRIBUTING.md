## 📝 Contribution Workflow

D-POAF follows a reviewable workflow: discussion → proposal → decision → versioned release.

### For Small Changes (Bug Fixes, Clarifications)

**Use GitHub Issues:**
1. Search existing issues to avoid duplicates
2. Create a new issue describing:
   - What needs to be fixed or clarified
   - Why it's important
   - Suggested solution (if any)
3. Maintainers will review and label appropriately
4. If approved, you can submit changes via Pull Request

**Good for:**
- Documentation typos or errors
- Broken links
- Small clarifications
- Template improvements

### For Significant Changes (New Concepts, Extensions)

**Use GitHub Discussions (RFC Process):**
1. Create a new Discussion in the "RFCs" category
2. Use this structure:
   ```markdown
   # RFC: [Your Proposal Title]
   
   ## Summary
   Brief description (1-2 sentences)
   
   ## Motivation
   Why is this change needed? What problem does it solve?
   
   ## Detailed Design
   How will this work? What changes are required?
   
   ## Impact on Canonical
   Does this require changes to frozen documents?
   
   ## Alternatives Considered
   What other approaches were considered?
   
   ## Adoption Strategy
   How should users adopt this change?
   ```
3. Community discusses and refines the proposal
4. Maintainers decide based on evidence and alignment with core principles
5. If approved, changes are tracked to a versioned release

**Good for:**
- New concepts or extensions
- Changes to core principles
- New roles or ceremonies
- Major documentation restructuring

### For Working Group Coordination

**Use GitHub Discussions:**
- Join or create working group threads
- Coordinate on specific topics (e.g., Certification, Tools, Adoption)
- Share progress and gather feedback

## 🔄 Pull Request Guidelines

If you're submitting changes via Pull Request:

### Before Submitting
- Ensure there's a related Issue or RFC Discussion
- Make sure changes align with D-POAF principles
- Check that you're modifying the correct document status:
  - **Frozen** documents (Canonical) require RFC and maintainer approval
  - **Active** documents can be updated with proper review
  - **Draft** documents are more flexible

### PR Description Should Include
- Link to related Issue or RFC Discussion
- Clear description of what changed and why
- Any implications for other documents
- For documentation: indicate if this is a correction vs. extension

### Review Process
- Maintainers will review based on:
  - Alignment with Canonical meaning
  - Evidence and rationale
  - Community feedback
  - Consistency with existing content
- Changes are tracked and released with version notes
