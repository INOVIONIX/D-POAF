# Contributing to D-POAF®

First off, thank you for considering contributing to D-POAF! 🎉

D-POAF is a community-driven framework built on principles of evidence-driven governance and collective intelligence. Your contributions help shape the future of AI-native software engineering.

---

## 🌟 Ways to Contribute

D-POAF welcomes contributions in several forms:

### Framework Development
- **Propose improvements** to the Canonical, Specification, or Terminology
- **Submit RFCs** for significant changes via GitHub Discussions
- **Share implementation experiences** and adoption stories
- **Contribute templates and examples** for practitioners
- **Report issues** or gaps in documentation

### Community Building
- **Answer questions** in Discord
- **Write tutorials and guides** about D-POAF adoption
- **Share case studies** from your implementations
- **Organize meetups** or study groups
- **Help onboard new members**

### Academic Research
- **Publish papers** using D-POAF as a foundation
- **Conduct empirical studies** on framework adoption
- **Develop theoretical extensions** to core concepts
- **Cite and reference** the framework in your work

## 📝 Contribution Workflow

D-POAF follows a reviewable workflow: discussion → proposal → decision → versioned release.

### For Small Changes (Bug Fixes, Clarifications)

**Use GitHub Issues:**
1. Search existing issues to avoid duplicates
2. Create a new issue describing:
   - What needs to be fixed or clarified
   - Why it's important
   - Suggested solution (if any)
3. Maintainers will review and label appropriately
4. If approved, you can submit changes via Pull Request

**Good for:**
- Documentation typos or errors
- Broken links
- Small clarifications
- Template improvements

### For Significant Changes (New Concepts, Extensions)

**Use GitHub Discussions (RFC Process):**
1. Create a new Discussion in the "RFCs" category
2. Use this structure:
   ```markdown
   # RFC: [Your Proposal Title]
   
   ## Summary
   Brief description (1-2 sentences)
   
   ## Motivation
   Why is this change needed? What problem does it solve?
   
   ## Detailed Design
   How will this work? What changes are required?
   
   ## Impact on Canonical
   Does this require changes to frozen documents?
   
   ## Alternatives Considered
   What other approaches were considered?
   
   ## Adoption Strategy
   How should users adopt this change?
   ```
3. Community discusses and refines the proposal
4. Maintainers decide based on evidence and alignment with core principles
5. If approved, changes are tracked to a versioned release

**Good for:**
- New concepts or extensions
- Changes to core principles
- New roles or ceremonies
- Major documentation restructuring

### For Working Group Coordination

**Use GitHub Discussions:**
- Join or create working group threads
- Coordinate on specific topics (e.g., Certification, Tools, Adoption)
- Share progress and gather feedback

## 🏷️ Issue Labels

When creating issues, maintainers will apply labels:

- `good-first-issue` - Perfect for newcomers
- `help-wanted` - Community assistance needed
- `bug` - Something isn't working correctly
- `enhancement` - Improvement to existing content
- `documentation` - Documentation improvements
- `canonical` - Related to Canonical Specification
- `terminology` - Related to Official Terminology
- `guide` - Related to Operating Guide
- `rfc` - Request for Comments (significant changes)

## 🔄 Pull Request Guidelines

If you're submitting changes via Pull Request:

### Before Submitting
- Ensure there's a related Issue or RFC Discussion
- Make sure changes align with D-POAF principles
- Check that you're modifying the correct document status:
  - **Frozen** documents (Canonical) require RFC and maintainer approval
  - **Active** documents can be updated with proper review
  - **Draft** documents are more flexible

### PR Description Should Include
- Link to related Issue or RFC Discussion
- Clear description of what changed and why
- Any implications for other documents
- For documentation: indicate if this is a correction vs. extension

### Review Process
- Maintainers will review based on:
  - Alignment with Canonical meaning
  - Evidence and rationale
  - Community feedback
  - Consistency with existing content
- Changes are tracked and released with version notes

## ⚖️ Code of Conduct

### Our Pledge
We are committed to providing a welcoming, inclusive, and harassment-free environment for everyone, regardless of background, identity, or experience level.

### Expected Behavior
- ✅ Be respectful and constructive in discussions
- ✅ Accept and provide constructive feedback graciously
- ✅ Focus on what's best for the D-POAF community
- ✅ Show empathy and kindness to others
- ✅ Respect different viewpoints and experiences

### Unacceptable Behavior
- ❌ Harassment, discrimination, or exclusionary behavior
- ❌ Trolling, insulting comments, or personal attacks
- ❌ Publishing others' private information without consent
- ❌ Any conduct that creates an intimidating or hostile environment

### Enforcement
If you experience or witness unacceptable behavior, please report it to:
- **Email**: contact@inovionix.com
- **Discord**: Message a moderator privately

All reports will be reviewed and handled confidentially. We're committed to maintaining a positive community.
